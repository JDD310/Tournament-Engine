# Tournament Engine

Tournament Engine is a web app for creating and running bracket tournaments. Organizers of esports and community events usually track brackets in spreadsheets or on paper, which gets messy fast, especially with Swiss stages where pairings depend on every team's record. Tournament Engine handles the bookkeeping so the organizer can focus on running the event, and gives players and spectators a live public page to follow results.

> **Status:** Planning stage (Unit 11). This README describes the planned app and will be updated as features are built.

## Planned Features

- **Single-elimination brackets** with automatic seeding placement and byes
- **Swiss stages** with record-based pairings, rematch avoidance, and Buchholz tiebreakers
- **Score reporting** that automatically advances winners
- **Live public tournament page** that updates as results come in (Server-Sent Events)
- **Public or private tournaments**, shareable with a link or QR code
- **Best-of-1/3/5 series** support

Organizers manage a tournament through a private admin link, so no account is needed to run an event.

| Database | PostgreSQL (hosted on Neon free plan) |
| Live updates | Server-Sent Events (SSE) |

| CI/CD | GitHub Actions |
| Hosting | Google Cloud Run (via Artifact Registry) |
| Project management | Jira + Confluence |
| AI tools (development only) | GitHub Copilot, Claude Code |

### Why these choices

- **FastAPI** handles async streaming well, which SSE needs, and it generates API docs automatically.
- **PostgreSQL** fits the data: matches reference teams and feed winners into later matches, and Swiss standings are aggregate queries that SQL handles well.
- **Neon** has a permanent free plan, and its compute scales to zero when idle and wakes back up on the next request, so the demo link keeps working without paying for an always-on database.
- **Cloud Run** runs the Docker container directly and has a free tier.

## Getting Started

### Local development

Requires Python 3.12+, Node 20+, and a Postgres database (a local one or a free Neon project).

**Backend** (FastAPI, runs on port 8000):

```
cd backend
python -m venv .venv && source .venv/bin/activate
pip install -r requirements-dev.txt
cp ../.env.example .env   # then set DATABASE_URL
alembic upgrade head      # create or update the database schema
uvicorn app.main:app --reload
```

The app does not create tables itself, so run `alembic upgrade head` after cloning and after pulling changes that add migrations. API docs are at http://localhost:8000/docs.

**Frontend** (React + Vite, runs on port 5173 and proxies `/api` to the backend):

```
cd frontend
npm install
npm run dev
```

### Database migrations

The schema is managed with [Alembic](https://alembic.sqlalchemy.org/). Migrations live in `backend/migrations/versions/` and read `DATABASE_URL` the same way the app does. Run these commands from `backend/`:

| Task | Command |
|---|---|
| Apply all migrations | `alembic upgrade head` (or `python -m app.migrate`) |
| Show the current revision | `alembic current` |
| Create a migration after changing `app/models.py` | `alembic revision --autogenerate -m "add best_of to tournaments"` |
| Check that the models and migrations agree | `alembic check` |
| Undo the last migration | `alembic downgrade -1` |
| Print the SQL without connecting | `alembic upgrade head --sql` |

Always read an autogenerated migration before committing it, since Alembic can't detect everything (renames, for example). The backend tests build their schema from the migrations, and `tests/test_migrations.py` fails if a model changes without a matching migration.

**On deploy**, run `python -m app.migrate` before the new version of the app starts serving traffic. Run it once per deploy (for example as a single Cloud Run job or a pre-deploy step), not in each instance's start command: there is no lock, so several instances starting at once would race on the `alembic_version` table. [docs/deploy.md](docs/deploy.md#6-run-the-migrations) sets this up as a Cloud Run job.

### Tests and linting

```
cd backend && pytest && ruff check .
cd frontend && npm test && npm run lint
```

Backend tests use in-memory SQLite by default. Set `TEST_DATABASE_URL` to run them against Postgres.

### Docker

The `Dockerfile` builds one image: a Node stage builds the React app, then a slim Python 3.13 image serves the API and the built frontend together on port `$PORT` (default 8080), as a non-root user.

1. Clone the repo: `git clone https://github.com/JDD310/Tournament-Engine.git`
2. Copy the environment file and add a Postgres connection string: `cp .env.example .env`. Inside the container `localhost` is the container itself, so for a database on your machine use `host.docker.internal` (Docker Desktop); a Neon URL works as-is. Don't put quotes around values; `--env-file` keeps them literally.
3. Build and run: `docker build -t tournament-engine .` then `docker run -p 8080:8080 --env-file .env tournament-engine`

The app is then at http://localhost:8080. With `MIGRATE_ON_START=true` (the `.env.example` default) the container runs the migrations before starting, which is fine for a single local container. To run them on their own instead: `docker run --rm --env-file .env tournament-engine python -m app.migrate`.

The image never contains secrets: `DATABASE_URL` comes only from the environment, and the container refuses to start without it.

### Deploying

The app runs on Google Cloud Run with the database on Neon. [docs/deploy.md](docs/deploy.md) is the step-by-step runbook (project setup, Artifact Registry, Secret Manager, migrations, deploy, verification and free-tier notes), and `scripts/deploy-cloud-run.sh` automates the repeat deploys.
